**Question 1 — Recap mutability: answer is (b).**

Recap is a projection overlay only. It never mutates stored corkscrews or any output table. The behavior is:

The liquidity event route loads current model state from the already-persisted output tables. For a recap event, it forks the debt corkscrew state in memory at `recap_period_index`, applies the new facility terms to that forked copy for the remaining periods, computes the dividend waterfall, and returns the full projected post-recap trajectory in the response. Nothing is written. The stored output tables are untouched.

The language in Section 20.5 ("new facility balance replaces old facility balance from recap_period_index onward") describes what happens inside the in-memory fork — not a write to the database. That section needs a clarifying note added but the intent is (b).

If you want to model what happens after a recap — new debt terms, new amortization, continued operations — you create a new model with a start date at the recap period and the new facility terms. The recap is a terminal read on the current model, not a mutation of it.

**Item A — DELETE + batch INSERT: yes, preferred over upsert.**

DELETE WHERE model_id = X and scenario combination, then batch INSERT the fresh rows. Cleaner than ON CONFLICT for large row counts because it avoids the index lookup overhead on every row. Batch size of 5,000 rows per insert call to stay within Supabase request limits. Wrap the DELETE + INSERT in a transaction so a failed write doesn't leave partial results.

**Item B — scenario_id on line items: your understanding is correct.**

`model_line_items.scenario_id = NULL` means the line exists in all deal structure scenarios — revenue lines, most expense lines. A specific `scenario_id` means the line only exists in that scenario — debt service lines, seller note interest lines, earnout lines that only appear in certain structures. The route handler filters `WHERE scenario_id IS NULL OR scenario_id = :currentScenarioId` before passing line items to the engine. `model_values` always has a concrete scenario_id because output is always scenario-specific. Proceed with that implementation.
